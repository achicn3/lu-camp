## 1. 已有能力與差異

| 項目 | 實際現況 | 本次處理 |
|---|---|---|
| 餐飲商品 | `menu.MenuItem`／`MenuOption` 已有名稱、售價、成本、介紹、圖片、每日限量 | 延用；不新增另一份商品或庫存主檔 |
| 分類／商品排序 | `MenuCategory.sort_order`、`MenuItem.sort_order` 及 PATCH API 已存在 | 管理畫面補操作；線上依設定排序，售完排在該分類尾端 |
| 零售咖啡豆／濾掛 | `inventory.CatalogProduct` 有售價、成本、`quantity_on_hand`；目前線上快照與訂單只支援 MENU | 另做第一階段零售整合波次；不得複製成餐飲商品冒充完成 |
| 加入購物車 | 只存瀏覽器，不扣庫存 | 保留；離開頁面也不會占住份數 |
| 現金送單 | Worker 驗價；限量單等 POS 匯入、原子保留才確認；結帳把保留轉正式銷售，淨額扣一次 | 延用已有並發保護，不為版面改動重寫已驗證流程 |
| 庫存同步 | POS 每 5 秒重取並推送；客人菜單每 15 秒刷新，非即時強一致 | 保留；送單及 POS 結帳仍需重驗，不以畫面剩餘量承諾成交 |
| 客人取消 | 客人頁無取消按鈕、公開 API 也不提供取消 | 明確禁止客人自行取消；店員可能已處理。店員誤單處理仍屬 POS 權限 |
| 製作狀態 | 沒有追蹤是否正在製作 | 不以未付款推定尚未製作，不在客人文案保證可取消 |
| 圖片 | 後端已有壓縮 WebP、去 EXIF、內容雜湊、雲端媒體儲存 | 延用；首屏少量載入，其餘 lazy load，固定尺寸防跳動 |
| 人氣／分析 | POS 有銷售資料；尚無線上曝光與推薦成效資料 | 第二階段；第一階段不得用手填數字假稱人氣排行 |

`frontend/app/(authed)/menu/page.tsx`；`online-order/src/client/`、`pricing.ts`、`menu.ts`。

## 3. 品牌與首屏

保留既有夜墨 `#0E0F10`、霧金 `#C4A766`、霧白 `#E7E3D8`，輔以石灰 `#AAA79E`、炭灰 `#202326`。
辰宇落雁子集字型用於店名、標題與商品名稱；問候、說明、操作與價格採同一套清晰系統字型，數字有穩定寬度。
不強制觀看 logo 動畫；菜單內容與操作不能等待裝飾性開場。

```text
露坑 LUKENG                         桌 A1

今天想喝什麼？
在露坑坐一下 ☕

[露坑推薦]       [咖啡]       [甜點]

露坑推薦       約 3 項，非強制湊滿
商品名 → 風味 → 適合誰 → 價格／加入

完整分類入口（由後台排序）
手沖體驗／咖啡／今日甜點／豆／濾掛／其他

                         [購物車 · N 份]
```

首屏先做選擇引導，完整商品列表放在進入分類後；無人工推薦時不假造「露坑推薦」。
分類不存在或沒有可展示商品時不硬造空入口；提供能往下選的備用分類。
推薦區不使用跑馬燈、倒數、閃爍、促銷紅色或大價格。主導視線的是商品與風味。
加入／增減／購物車／送單有至少 44px 操作區，考量底部安全區、鍵盤、焦點與 reduced-motion。

## 4. 商品呈現資料，不是新商品庫存

在 `onlineorder` 延伸可發布的呈現設定，**引用既有商品**：

- 原品項引用：店別＋`menu_item_id`；M1d 加入店別＋`catalog_product_id`，必須且只能選一種來源。
- 可選預選 `menu_option_ids`，供手沖體驗用；全部屬於該店、可掛在該品項，且符合原選項規則。
- 展示名稱、風味短文、適合族群、體驗包含內容。沒有資料就省略，不自動杜撰。
- 推薦、新品、今日限定開關；限定生效日依台北營業日判定，過期不再顯示。
- 顯示剩餘量開關、低庫存門檻（預設 5，可逐品項調整）、售完是否隱藏。
- 展示排序與加購資格；有序推薦目標引用（跨店、自己推薦自己、已封存目標需驗證）。
- 第二階段規則預留：風味偏好、是否體驗、黑咖啡／奶咖啡；不先堆無人使用的資料表或分析工具。

呈現設定**不含另一份可維護售價、成本、庫存**。售價與成本由原品項及選項計算；
圖片可延用既有照片機制，分類排序優先用現有排序 API。資料庫約束、store scope、管理權限及稽核必須齊備。
公開快照採允許欄位清單，不公開成本、內部備註或管理者資料。OpenAPI 更新後重新生成 POS client。

### 手沖體驗

呈現「蜜桃手沖體驗」，顯示完整總價與「咖啡豆、完整器材使用、現場體驗」；
來源仍是原品項＋已驗證選項組合，不要求店員維護兩份庫存。
未指定的必選項仍需選擇；選項失效、停售或售完時，體驗也不能售出。
購物車、客人訂單、POS 顯示名稱要可辨識這是體驗；成交保留原商品與選項 ID、成本快照及金額。
**咖啡飲用的豆種選項不等於一包零售咖啡豆**，不互相挪用庫存。

## 5. 剩餘數量、售完與競爭

| 當前可售量 | 客人顯示（開啟顯示且門檻為 5） |
|---|---|
| 不限量或 > 5 | 不顯示數量 |
| 2–5 | 今天剩 X 份 |
| 1 | 最後 1 份 |
| 0 | 今日售完，停用加入 |

隱藏數量只影響 UI：**不能把 `remaining` 改成 null**，現有驗價把 null 視為不限量，會影響保留判斷。
也不能修改真正庫存來製造稀缺。品項與選中選項的共同限制要一起算，別只看品項剩餘量。
售完預設保留卡片、降低視覺權重，穩定排到該分類尾端；開啟「售完隱藏」才隱藏。
首頁推薦、加購、引導結果共用同一可售判斷，不能在首頁隱藏卻從推薦重新出現。

加購與加入購物車都不扣庫存。送單前取得現況並重驗；若庫存不足，保留其他選擇、定位問題品項，
顯示「這個商品剛剛售完了，請調整購物車。」可單獨移除或減量，不要求清空整車。
POS 匯入時最後一份由原子保留決定唯一贏家；輸家不得成立銷售或扣款。
狀態分清楚「已收到、確認份數中」與「已確認、待付款」，送單成功不等於已付款。
保留到期、付款不明、取消與退款沿用 O4 保護；不因客人看不到數量而解除任何伺服器檢查。

## 6. 加購

先用管理者設定與明確商品角色（咖啡／甜點／體驗／豆／濾掛），不猜名稱關鍵字。
預設方向：咖啡→甜點、甜點→咖啡、體驗→豆／濾掛、豆→濾掛／其他豆款。
只在完成主要選擇後或購物車下方顯示，最多 1–2 項；排除已選、售完、停售、封存及不允許推薦的品項。
文案使用「配個甜的？」或「要不要再帶一個？」；未有數據前不使用「很多人會買」。
不要自動加進車內、不預勾、不捏造折扣；「一起帶」走同一選項驗證與計價。略過後不反覆打擾。

## 7. 第二階段的資料設計

人氣來自 POS 真實 `sale_lines`，按店別、原商品類型／ID、台北時間窗計算；
排除作廢，退貨以淨銷量處理，贈品與體驗同源多呈現如何合併需在實作測試中明確定義。
第一名「人氣 No.1」、二三名「人氣推薦」；樣本不足不顯示。不得由手填推薦旗標偽裝成銷量排名。

事件合約先保留以下形狀，待 M2b 才開啟收集與建立必要儲存：

```text
event_id, event_type, occurred_at, schema_version,
store_id, anonymous_session_id, menu_version,
source_product_type, source_product_id, presentation_id?,
placement?, recommendation_rule_id?, experiment_id?, variant_id?, quantity?
```

事件：商品曝光（可見才算）、商品點擊、加／移購物車、推薦曝光／點擊、問答開始／完成。
成交與成交數量以伺服器銷售為準，不信任瀏覽器 purchase 事件；不紀錄備註、付款權杖或其他個資。
事件去重、批次非阻塞送出、限流、保留期限與用量上限均需在收集上線前完成。
推薦點擊率分母為推薦曝光；加購成功率以加購來源最終成交定義，不能把點擊當成交。
A/B Test 放最後，先有可用的事件品質與足夠樣本。

## 8. 每波驗收

1. migration 可升級、舊商品有保守預設；管理者可改、跨店拒絕、非法組合拒絕、重開設定仍在。
2. 店內發布→Worker 快照／可售覆蓋→客人頁一致；舊快照相容、成本與內部資訊不外洩。
3. 375／390／430px 真瀏覽器：QR 進入、首頁／分類、加入、選項、減量／移除、加購、返回、送單與狀態。
4. 最後一份多人爭買、同選項跨品項、同商品不同呈現、回應遺失重試、暫停、售完／恢復與跨日。
5. 同筆銷售的金額、原商品 ID、成本、庫存變化、營收分類、稅與發票與改版前相符；作廢／退款不重複回補。
6. 圖片 lazy load、首屏請求量與可操作時間實測；不以假資料頁的速度宣稱正式效能。
7. lint／型別／測試／API 漂移＋適當覆蓋率；真 backend、Postgres、Worker 煙霧與截圖，金額／併發改動獨立審查。

每波分開提交可回退；新呈現未發布前舊頁正常使用。正式合併／部署另依現有流程完成，
不能因菜單看起來完成就跳過 POS、庫存、報表或發票驗證。

## 9. M1a 交付紀錄（2026-10-07）

## 10. M1b 與餐飲管理 UX（2026-10-07）

- 客人首頁先顯示問候、入口與最多三項人工指定且可售推薦；沒有推薦不補假推薦。咖啡／甜點入口引用同名現有分類，缺少時使用實際有展示品項的分類。完整品項在進入分類後顯示，分類與原商品排序仍由 POS 維護。
- 移除阻擋操作的開場；夜墨／霧金與手寫商品名沿用品牌設定。沒有照片不占空圖框，推薦最多三張圖片優先載入，其餘 lazy load、固定尺寸。
- 商品卡分開詳情與加入按鈕：無選項直接用既有 `addLine` 驗證加入，有選項先開詳情；售完停用加入。價格／數量與訂單仍引用原商品及選項。
- 首頁／分類／購物車支援返回、瀏覽器前進後退與重新整理，維持 QR 桌碼與購物車。供應刷新不重設分類與詳情數量；售完／恢復及選項狀態會同步，關閉詳情有焦點備援。
- 購物車失效時保留全部選擇與所選選項，逐行提示並允許減量／移除；未修正前不顯示送單操作。客人訂單仍沒有取消功能。

## 13. M1d 零售商品上線與「帶回家」交貨（2026-10-08 店主裁示，設計）

**資料（店內 Postgres）**

  商品停售（`is_active=false`）或庫存 0 → 線上顯示售完／不列。
- `online_orders` 加 `fulfillment_status`：`NONE`（沒有帶回家商品）／`AWAITING`（有、尚未交貨）／`HANDED_OVER`，
  加 `handed_over_at`、`handed_over_by_user_id`。
- `StockReason` 加 `ONLINE_HOLD`／`ONLINE_RELEASE`。

**保留與扣庫存**（照 O4 餐飲份數的做法）：POS 拉到含帶回家商品的單時，在同一交易內**直接扣 `quantity_on_hand`**
並記 `ONLINE_HOLD` 異動；取消／到期加回（`ONLINE_RELEASE`）；帶入結帳時先加回、再照一般結帳扣（`SALE`），淨額只扣一次。
櫃檯因此不會把線上保留的最後一件賣掉，銷售流程不用改。保留明細記在既有 `stock_reservations.consumed`（`kind=catalog`）。
跨模組一律呼叫 `InventoryService` 的新方法，不直接碰 `catalog_products`。

**發佈快照**：多 `retail` 清單（listing id、product id、名稱、含稅單價、介紹、分類名、角色、照片雜湊、可售數），
不含成本、SKU、內部備註。字型子集包含名稱與介紹。

**雲端**：快照驗證 `retail`；送單行 `{"catalog_product_id", "qty"}`（無選項），雲端用快照驗價與可售數；
D1 `order_lines` 加 `catalog_product_id`（migration 0006），`orders` 加 `fulfillment`（店內回報）。客人訂單頁：
有帶回家商品就顯示「帶回家商品請到櫃檯領取」，交貨後顯示「已領取」。

**POS**：帶入結帳時零售行變成一般商品行（`C:{id}`）；線上訂單清單在付款後保留「待交貨」的單，列出要交的商品，
按「已交貨」（寫稽核）→ 結單並回報雲端。餐飲行照舊不追蹤出餐。

- **客人頁**：首頁入口「不知道喝什麼？」→ 一題一題問（可上一題、先不用）→ 每個答案勾的品項各加 1 分，**分數高的最推薦、
  同分照勾的先後**，再給最多 2 個備選；售完、下架的不推。對不上就說「今天沒有剛好符合的」並給完整菜單，不捏造推薦。
  結果卡可直接加入；可重新回答。
- **驗證**：後端 quiz／發佈測試、Worker 49＋5 測試、POS 6 測試、`online-quiz-smoke.mjs` 8/8。升級 docs/76。
- **已知風險（店主裁示不修，Codex 第一輪）**：客人答到一半時剛好重新發佈且改了題目／答案順序，已選的答案會對到新選項、
  推薦不準（不影響點餐與金額）。

## 15. M2b 人氣標籤（2026-10-10 店主裁示）

**裁示**：①這一波**只做人氣排行、只用 POS 真實成交**，不收集客人瀏覽／點擊（推薦成效分析不做）；**可從後台控制**；
②近 **30 天**；③淨銷量**至少 10 份**才上榜；④**每個分類前三名**掛標籤（第一名「人氣 No.1」、二三名「人氣推薦」）。

- **算法**：餐飲品項近 N 天（台北日，含今天）淨銷量＝成交份數（沒作廢、一般銷售不含贈品）− 那段期間成立的銷售被退的份數；
  同分照菜單排序。只算餐飲品項（體驗卡賣出也記在原品項上）。
- **後台**：菜單 →「線上發布」→「人氣標籤」：開關、計算期間（7／14／30／60／90 天）、門檻（1–999 份），並列出目前的榜
  （不論開關都看得到，方便預覽）。管理者才能改，寫稽核 `UPDATE_ONLINE_MENU_POPULARITY`。表 `online_menu_popularity`
  （沒有列＝預設：開、30 天、10 份），migration `b6d0f4a8c2e5`；API `GET/PUT /online-order/popularity`。
- **到客人頁**：名次跟著可售狀態同步（`popular: [{id, rank}]`）每幾秒推上雲端，**賣出就更新、不必重新發佈**；
  雲端把名次套到品項（`popularity`），品項卡在人工標籤前面顯示。關掉就送空的、標籤消失。
- **部署順序：雲端 Worker 先上，再升店內**——舊 Worker 不認得 `popular`，會把整份可售狀態拒收（售完同步也會停）。
- **Codex 第一輪（店主裁示）**：下架的品項不再佔名次、沒設分類的品項自成「未分類」一組取前三 → 已修。
  **已知風險（不修）**：改了品項分類卻沒重新發佈時，雲端照舊分類顯示，同一分類可能看到兩個 No.1，重新發佈即恢復。
- **驗證**：後端人氣測試 8 支、Worker 233、POS 4 支、`online-popularity-smoke.mjs` 6/6。升級 docs/77。
