# 42 — 收購佇列：現場收件、估價、付款；商品建檔與上架留到空檔

> 狀態：**規格草案，待店主確認**（2026-09-24）。確認前不動工。
> 目標：**現場少填資料、商品不混批、金額查得回來、之後上架不必重做。**

## 1. 為什麼要有這條流程

目前的收購頁是「一次做完」：付款、簽署、建庫存（每件都要成色、售價、分類）在同一個步驟。
客人一次帶十幾件來時，店員得當場把每件都建檔完，後面的客人只能等。

收購佇列把工作拆成兩段：

- **現場（有客人在等）**：收件 → 估價 → 報價 → 簽署 → 付款。只填足以辨認商品與決定價格的資料。
- **空檔（打烊、非收購日，甚至隔週）**：把已付款的商品補齊資料、入庫、印標籤。

**現有收購頁的直接收購流程完全不變**，仍可單獨使用（§9）。

## 2. 店主裁示（2026-09-24）

| # | 議題 | 裁示 |
|---|---|---|
| 1 | 何時付款 | 客人確認明細並簽署後，**當場付款**；付款方式沿用現有功能（現金／購物金／混合） |
| 2 | 號碼牌 | 收購用 **A 字首**（A001…），每天重編，與餐飲叫號分開；內部批次編號永久唯一 |
| 3 | 列印 | **收據機印兩份相同的收件單**：一份給客人、一份放在商品上；同一批只有一個號碼、一個條碼，可「補印」 |
| 4 | 類型 | **買斷、寄售、散裝都走佇列**（做法相同） |
| 5 | 成交收購價 | **店員也可以改**；系統建議價與最後成交價都保留 |
| 6 | 照片 | 先不做 |
| 7 | 客顯 | 第一期不串客顯；成交明細在簽署頁給客人看；毛利與歷史資料不給客人看 |
| 8 | 現有收購頁 | 直接收購流程不動；只多一個「來自待整理庫存」模式（送出不再付款、不再簽署） |
| 9 | 存放位置 | 不做 |
| 10 | 成色／分類 | 估價時可順手點、**不強制**；成色沒點時依折數推斷——與收購頁**同一支程式** `gradeFromDiscount` |
| 11 | 待整理庫存 | 要一張清單：可查詢、可編輯、可一鍵帶入收購頁上架 |

## 3. 流程

| 階段 | 店員操作 | 系統處理 | 批次狀態 |
|---|---|---|---|
| ① 報到收件 | 查詢／新增會員；**和客人一起點清實收件數** | 建立批次、發當日號碼、印兩份收件單 | 待估價 |
| ② 估價 | 每列填簡稱、數量、原價、點**售價折數** | 算預計售價、建議收購價；**隨時存檔，可中途離開再回來** | 估價中 |
| ③ 叫號確認 | 叫號、報價；每列標處置，可部分接受 | 重算成交總額 | 待確認 |
| ④ 簽署 | 客人在簽署裝置看成交明細並簽名 | **保存簽署當下的明細版本** | 已簽署待付款 |
| ⑤ 付款 | 付款方式沿用現有功能 | 成立收購（錢櫃／購物金紀錄）；成本與件數入帳為「待整理庫存」 | 已付款待整理 |
| ⑥ 補資料上架 | 空檔時從待整理庫存清單「上架」，帶進收購頁補資料 | **接續同一筆收購**：不再付款、不再簽署；可分次上架 | 部分上架 → 全部上架 |

收件後批次**立刻進佇列**（不必估完才排隊），第一位客人的十幾件估到一半就能先接下一位。

例外狀態：**取消**（客人放棄整批）、**叫號未到**（保留在待確認，不自動取消）。

## 4. 估價：每一列商品

| 欄位 | 現場 | 說明 |
|---|---|---|
| 商品簡稱 | **必填** | 「黑色折疊椅」；隔週上架時才認得出是哪件 |
| 數量 | 必填，預設 1 | 只有同款、同狀況、同價格才合併；一件有破損就拆成兩列 |
| 類型 | 必填，預設買斷 | 買斷／寄售／散裝（見 §10 待確認 1） |
| 原價／件 | 用折數估價時必填 | 明確標「原價／件」 |
| 預計售價折數 | 用折數估價時必填 | 快捷按鈕；**五折＝預計賣 500 元，不是用 500 元收購** |
| 預計含稅售價／件 | 自動 | 原價 × 折數，無條件進位到 10（沿用 ADR-023） |
| 建議收購價／件 | 自動 | 沿用收購頁同一套計價（`acquisitionFromListedPrice`：扣稅、手續費、目標毛利率） |
| 成交收購價／件 | 預設＝建議價 | 店員可改；兩者都保留 |
| 成色 | 選填 | 沒點時依折數推斷（同收購頁 `gradeFromDiscount`：≥7 折 S、≥5 A、≥3 B、其餘 C） |
| 分類 | 選填 | |
| 品牌、型號 | 選填 | 有填才顯示歷史行情；**只當參考，不覆蓋已填的估價** |
| 配件／特殊狀況 | 選填 | 「缺收納袋」 |
| 寄售抽成 % | 寄售必填 | 預設取設定值，同收購頁 |

- 折數 **≥ 六折** 時紅字提醒「折數偏高，可能是新品，請確認成色」（收購頁同步加上）。
- 歷史行情顯示：上次收購價、當時預計售價與折數、實際賣出價（如已售出）、日期、成色、備註。
- 「幾項」與「幾件」分開：黑色折疊椅 ×2、露營桌 ×1 → 共 2 項、3 件。報到時的實收件數是點清的數字；
  簽署一律用**實際成交件數**。

## 5. 叫號確認：每列處置

| 處置 | 意思 |
|---|---|
| 接受 | 成交（可部分：3 張收 2 張） |
| 客人不售 | 客人帶回 |
| 店家不收 | 店家不收，退回客人 |
| 待確認 | 還沒談定 |

部分接受或不收的數量，要勾「已退還客人」。**取消整批也不代表東西已經領回**，一樣逐列記退還。
不刪除任何列：之後才查得到當時收了什麼、退了什麼。

## 6. 簽署與付款

- 簽署頁：共幾項、幾件、總收購價；底下列出成交明細（簡稱、數量、單價、小計）。付款方式（現金／購物金）
  也在簽署內容裡，沿用現有收購切結的規則。
- 簽署時保存**明細版本**。簽完要改品項或金額 → 必須重新簽署；付款後要更正 → 走作廢收購（有紀錄）。
- 付款時成立收購：錢櫃／購物金紀錄與現在完全相同；**成本與件數在這一刻入帳**（待整理庫存），不是等上架才記。
- 未開帳時不能付現（沿用不變量 8）。

## 7. 待整理庫存

付完錢、還沒上架的商品。清單可以：

- 依「放最久」「賣方」「收件日」排序篩選；超過 **14 天**未上架標示提醒。
- 掃收件單條碼直接打開那一批。
- 編輯每列資料（簡稱、成色、分類、品牌型號、預計售價、備註）；**成交收購價與件數不能在這裡改**（那是客人簽過的）。
- 勾選要上架的列 → **一鍵帶入收購頁**。

## 8. 上架（帶入收購頁）

帶入時自動填好：會員、批次、簡稱（→品名）、原價、折數、預計售價、成交收購價與數量、已填的成色／分類／品牌型號／備註。
收購頁在這個模式下：

- 不顯示付款與簽署區塊；送出＝**把這些列建成庫存、印標籤**，掛在原本那筆收購下。
- 每列顯示「還缺什麼」（缺分類、缺成色），缺資料的排前面；可**整批套用**分類／成色再個別修改。
- 品名自動建議品牌型號（沿用現有品名建議與歷史紀錄）。
- **分次上架**：勾幾列就上幾列；清單顯示「已上架 4 件、待整理 6 件」。
- 同一列不會因重複點擊、重新整理或兩名店員同時操作而重複入庫（每列記已上架數量，送出以鎖＋冪等鍵保護）。
- 上架時發現少件或商品不符：**另記差異**（件數、原因），不改原成交件數；成本不覆寫。
- 可改：上架售價、成色、分類、品牌型號、品名、備註。

## 9. 現有收購頁

直接收購流程**一行不改**。只新增「來自待整理庫存」模式（§8），由待整理庫存清單帶入才會出現。
計價（`features/acquisition/pricing.ts`）、成色推斷、簽署、付款、入庫共用同一套程式，不另寫。

## 10. 待確認

1. **同一批混類型**：同一位客人同時帶買斷與寄售的東西，要不要放同一批？
   - 建議：**可以**，一次簽署；付款時系統依類型各成立一筆收購（買斷一筆、寄售一筆、散裝一筆），都掛在同一批。
     這需要放寬「一筆簽署只綁一筆收購」的資料庫限制。
   - 若第一期不混：報到時選類型，混類型的客人開兩批。
2. **付款後、上架前要作廢**（例如客人隔天反悔）：沿用作廢收購——退回現金／購物金、待整理庫存一併取消。可以嗎？

## 11. 對現有程式的影響（初步）

| 範圍 | 沿用 | 新增／修改 |
|---|---|---|
| 會員 | 查詢、新增（含身分證盲索引去重） | — |
| 計價 | `pricing.ts`（折數、進位、反推收購價、成色推斷） | 後端需同一套公式驗證成交價（目前前端算、後端只收結果；見下） |
| 簽署 | 簽署裝置流程、切結書版本 | 簽署內容改由批次成交明細產生；比對對象改為批次版本 |
| 付款 | 現金／購物金／混合、錢櫃紀錄、開帳守衛 | 付款與建庫存**拆成兩段**：先成立收購（有付款、無庫存），上架時才建序號品／散裝批 |
| 庫存 | 序號品、散裝批、標籤列印 | 上架端點：依待整理列建庫存、記已上架量、防重複 |
| 報表 | 收購紀錄、庫存價值 | 庫存價值加「待整理庫存」一欄（已付成本不能消失）；收購紀錄顯示上架進度 |
| 作廢 | 作廢收購（對稱反轉） | 含待整理列的收購作廢時一併取消 |
| 列印 | 收據機、條碼 | 新增「收件單」列印（代理新端點） |
| 叫號 | — | 收購用 A 字首當日編號（獨立於餐飲叫號） |
| 新資料 | — | 收購批次、批次明細列（含處置、退還、已上架量）、簽署明細版本、上架差異 |

> 計價在後端的角色：目前收購頁由前端算建議收購價、後端收店員送出的收購價。佇列沿用這個分工
> （成交價本來就可由店員改），後端只驗證金額合法與總額一致，不重算建議價。
