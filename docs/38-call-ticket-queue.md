# 38 — 叫號系統（收購前候位清單）

> 客人想賣東西 → 店家請他先填表單 → 客人把連結傳給店家 → 店家登記（名稱／連結／備註）
> → 系統給一個號碼 → 處理完按「完成」。
> 用途是**排隊喊人**，不是收購流程本身。

---

## 1. 店主裁示（2026-08-19）

| 項目 | 裁示 |
|---|---|
| 號碼規則 | **每日重置，從 1 開始** |
| 完成之後 | **從清單消失，但資料留著**（事後查得到那個表單連結） |
| 與收購的關係 | **先不串**，獨立清單 |
| 權限 | **店員也可以**登記與完成 |

---

## 2. 資料模型

### 2.1 `call_tickets`

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | int PK | |
| `store_id` | int FK → `stores` | **必填**（CLAUDE.md §4：每張業務表都要有） |
| `ticket_date` | date | **台北營業日**，每日重置的依據 |
| `ticket_no` | int | 當日序號，從 1 開始 |
| `name` | str(60) | 客人稱呼；必填 |
| `link` | str(500) \| NULL | 客人填的表單連結 |
| `note` | str(500) \| NULL | 備註 |
| `status` | enum | `WAITING` / `DONE` |
| `created_by_user_id` | int FK | 誰登記的 |
| `created_at` | datetime | UTC |
| `completed_by_user_id` | int FK \| NULL | 誰按的完成 |
| `completed_at` | datetime \| NULL | UTC |

**唯一索引**：`(store_id, ticket_date, ticket_no)`。

### 2.2 營業日以台北時區切

`ticket_date = store_date(created_at)`（`core/time.py` 既有）。
**不可用 UTC 日期**——台灣時間 08:00 之前的 UTC 日期還是前一天，號碼會在早上莫名接續昨天。
報表那邊踩過同一個坑。

### 2.3 號碼配號

同一 `(store_id, ticket_date)` 取 `MAX(ticket_no) + 1`。
單店單機，並發極低，但**唯一索引是最後防線**：撞號時重取一次號再寫入（最多重試 2 次），
不可把 `IntegrityError` 吞掉或直接回 500。

### 2.4 連結必須驗證 scheme

`link` 會被店員點開，**只接受 `http://` 與 `https://`**。
`javascript:`、`data:`、`file:` 一律拒絕（422）——那是會在店員瀏覽器上執行的東西。
空字串正規化為 `NULL`（不要存 `""` 又在畫面上顯示成可點的空連結）。

---

## 3. API

全部**不限店長**（`CurrentUserDep`，`CLERK` 可用；`KIOSK` 由中央守衛擋掉）。

| 方法 | 路徑 | 用途 |
|---|---|---|
| `POST` | `/api/v1/call-tickets` | 登記一筆，回配到的號碼 |
| `GET` | `/api/v1/call-tickets` | 清單；預設**只回 `WAITING`** |
| `POST` | `/api/v1/call-tickets/{id}/complete` | 標記完成（冪等：已完成再按回原狀態，不報錯） |

`GET` 支援 `include_done=true`＋`date=YYYY-MM-DD`，供事後回頭找那個表單連結
（裁示「資料留著」的落點——沒有這個查詢，資料等於留了也找不到）。

**完成是冪等的**：兩台裝置同時按、或店員手滑連按兩下，不該有人看到錯誤。

---

## 4. 畫面

新增頁面與導覽項目「**叫號**」。

### 4.1 登記

三個欄位（名稱必填、連結與備註選填）＋「取號」按鈕。
送出後**把號碼大大地顯示出來**——這個數字是要喊出口的，不是給人瞇著眼找的。

### 4.2 清單

預設只顯示**未完成**的，每列：號碼、名稱、連結（可點，`target="_blank"` ＋
`rel="noopener noreferrer"`）、備註、登記時間、「完成」按鈕。

**跨日未完成的仍留在清單**（否則客人的單會憑空消失），但號碼前面加日期以免與今日的混淆：

```
#3        王先生    （今日）
8/18 #7   陳小姐    （昨天沒處理完的）
```

> 這一項屬設計判斷，非店主裁示：若希望跨日自動消失，改成只查今日即可。

### 4.3 完成

按下即從清單移除。**不做二次確認**——這不是不可逆的破壞性操作，資料還在，
按錯了用 `include_done` 查得回來。

---

## 5. 不做的事（本版）

- **不與收購串接**（裁示）：按完成不會跳轉、不帶資料
- **不在顧客螢幕顯示叫號**：目前顧客螢幕的用途是購物明細與簽署，插入叫號會打亂它的狀態機
- **不列印號碼牌**：客人的號碼由店員口頭告知或自己記；要印再說
- **不做等待時間統計**

---

## 6. 測試

- **service**：配號從 1 開始、同日遞增、跨日重置、跨店互不影響；完成的冪等性；
  撞號時重取號成功
- **邊界**：台北時間 00:00 與 08:00 前後各建一筆，`ticket_date` 必須是台北日
- **連結**：`javascript:` / `data:` / `file:` 被擋成 422；`http`/`https` 通過；空字串存成 NULL
- **權限**：`CLERK` 可登記與完成；`KIOSK` 被擋
- **API**：清單預設不含已完成；`include_done=true` 查得到
- **瀏覽器 E2E**（CLAUDE.md §1 強制，有 UI）：登記 → 看到號碼 → 完成 → 從清單消失 →
  勾「顯示已完成」→ **從畫面上**找得回那筆與它的表單連結
- **跨日汙染（店主特別要求，2026-08-19）**：最危險的樣子是「昨天的 #3 沒處理完、
  今天又有一個 #3，店員喊 3 號時兩個人站起來」。以回填日期製造前一天的資料，
  從畫面驗證四件事：
  1. 今天的號碼**只依當日流水**，不接續昨天
  2. 昨天沒處理完的**仍在清單**（客人真的還在等），但號碼**標了日期**
  3. 昨天**已完成**的不混進今天的候位清單
  4. 同號不同日在畫面上分得開
     ——並先斷言「本輪真的製造出撞號」，否則第 4 條會因為沒撞到而空過
