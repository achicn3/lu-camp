# ADR-022：開店前檢查的三個邊界（裝置不經後端、狀態每店每日、導向記瀏覽器）

- **Status**: Accepted（2026-09-18）

- **Context**:

  店主要求：每天第一次打開系統要跳出一份開店前檢查，全部綠燈才消失；項目包含開帳、
  各機器狀態，並可在設定頁自行增減待確認事項（docs/10 的 /opening-check）。

  裁示四項（2026-09-17）：

  1. 未完成**不擋**其他頁面——每天只自動帶一次，導覽列留紅點。
  2. 自動項目沒過可以「今天略過」，**不必填原因**。
  3. 完成狀態以「每店每日」為單位：店裡有收銀電腦＋客顯平板＋收購平板，任一台做完就算做完。
  4. 自訂項目由店主在設定頁增減。

  實作上有三個位置要決定：機器狀態由誰去問、狀態存在哪、「今天導過了沒」記在哪。

- **Decision**:

  1. **機器狀態由前端直接問 hardware-agent，不經後端。**
     代理跑在店內電腦上、與列印同一條路（`/devices/status` 早就存在，只是沒人呼叫）。
     繞後端只會多一層可能說謊的快取。連不到代理時 `fetchDeviceStatus` 回 `null`
     （代表「問不到」），**不是空陣列**；代理回空清單同樣視為問不到。

  2. **完成狀態存後端，每店每日一列**（`opening_checks`，唯一鍵 `(store_id, business_date)`）。
     營業日以店面時區計（`core.time.store_date`）。已勾的自訂項目與今天略過的自動項目
     各存一個陣列；自動項目「有沒有通過」是即時判定的，不落庫，只有「略過」要記。

  3. **「今天導過了沒」記在瀏覽器 localStorage。**
     導向是**這台裝置**的行為（客人不會希望收銀機跳走，但平板該跳），完成狀態才是店的行為。
     讀不到 localStorage（無痕／封鎖）時選擇**不導向**，而不是每次換頁都導。

  4. **開帳要分三態**：今天開的、還開著但是前一天的、沒開帳。只看「有沒有 OPEN 的班別」
     會把昨天忘記關帳當成今天已開好，今天的現金收入被算進昨天的班別（違反 §7 不變量 4）。

- **Consequences**:

  1. 後端的 `completed` **永遠只是部分事實**（不含機器狀態）。任何要宣稱「全綠」的畫面
     都得自己問代理。反過來，**「問不到代理」不得當成未完成**——手機、平板上根本沒有代理，
     把它算成未完成的話那些裝置會天天亮紅點、天天被導走，而且畫面上一列機器都不會出現，
     連略過的按鈕都按不到，永遠解不掉。（這正是 2026-09-18 審查的 N2：第一版就踩了。）
     因此頁面的「全綠」與導覽列的「該提醒」是**兩個判斷**，共用同一支
     `features/openingcheck/status.ts`，不可各寫一份。

  2. 狀態用陣列欄位（Postgres 陣列不能掛外鍵）：
     - 所有寫入路徑**必須上 row lock**（`get_check(..., for_update=True)`），否則兩台裝置
       同時打勾會靜默吃掉一筆——而多台共用一份狀態正是這功能的賣點。
     - `GET /today` 維持**唯讀**（查不到就回預設值），否則當天第一個早晨兩台同時開頁會
       互撞唯一鍵吃 500；這支 query 掛在每一頁的殼層，觸發頻率很高。
     - 自訂項目刪除採封存，讀取時與現存項目取交集，殘值不會讓今天永遠完成不了。

  3. 導向記在瀏覽器：清快取、換瀏覽器、無痕都會各自再跳一次，也無法跨裝置去重。
     這是刻意換來的「不擋人」——寧可多跳一次，也不要把沒做完的檢查變成營業的門檻。

  4. 「測試模式」（fake driver）的機器**不算通過**：這頁的承諾是「全綠＝可以開店」，
     而測試模式按了不會出紙。正式機接上真機後不受影響。

- **Alternatives considered**:

  - *後端代打代理*：後端與代理不在同一台機器上（代理在店內、後端可能在別處），
    後端問不到反而更常見，且多一層快取會讓「現在到底通不通」更難解釋。
  - *完成狀態記在瀏覽器*：最省事，但每台裝置都要各做一次，店主也看不到今天做了沒——
     與裁示 (3) 直接衝突。
  - *未完成就擋住 POS*：店主否決。印表機故障那天會直接癱瘓整間店。
