# ADR-034：行事曆（agenda）、員工名單（staff）與單一付款帳（expenses）

- 狀態：已採納（店主兩輪問答＋六題「都照預設」2026-10-30；規格見 docs/99）
- 相關：ADR-030（採購單事後修改、進項發票獨立成表）、CLAUDE.md §2（模組邊界）、§7-4（現金對帳）、§7-8（影響現金須開帳）

## 背景

店主要一個行事曆：記待辦、什麼時候下單、付了多少錢、什麼時候到貨，並延伸到固定帳單、排班、客人預約、
到期與保養。查證現況：採購單只有送出時間與收貨時間，**沒有付款、應付、預計到貨日**；付廠商現金只能記
「取出現金」（MANUAL_ADJUST，且只有管理者能用），匯款、刷卡沒地方記；不進庫存的花費完全沒有紀錄；
系統只在店內網路。

## 決定

1. **三個新模組**：`agenda`（待辦、事件、重複規則、行事曆彙整、今天）、`staff`（員工名單；第三期加排班）、
   `expenses`（付款、分配、結清；第二期加支出單、固定帳單、類別）。`purchasing` 只擴充日期與付款條件欄位。
2. **付款只有一本帳**：採購單的付款也記在 `expenses.payments`，以 `payment_allocations` 分到一張或多張單
   （採購單、第二期起的支出單）。月結一筆匯款付多張、訂金尾款、每月支出報表都從同一份資料來，不會兩邊對不起來。
3. **依賴單向**：`expenses → purchasing`（驗證採購單、取金額）、`agenda → purchasing／expenses／campaigns／consignment`
   （唯讀彙整）。**`purchasing` 不依賴 `expenses`、`agenda`**；採購頁要顯示的付款資訊由前端呼叫 expenses API 組合。
4. **抽屜現金付款連動對帳**：新增 `CashMovementType.EXPENSE_PAYMENT_OUT`、`EXPENSE_PAYMENT_VOID_IN`，必須在開帳中的
   班別；應有現金公式納入兩者（未知類型仍拒絕）。付款金額不能改，錯了作廢重記；作廢只限管理者，現金退回記在作廢當下的班別。
5. **店員貨到付現的例外**（裁示 10）：店員只能記「抽屜現金、單一採購單、付款條件為貨到付款、金額 ≤ 還欠」的付款，
   其餘付款與作廢只限管理者。現行「取出現金只限管理者」的控管不變。
6. **重複待辦不預先展開**：只存規則；某一次被打勾、略過或修改時才建列（`series_id`＋`occurrence_on` 唯一）。
   過去未建列的視為已過期，未來的在彙整時算出來顯示。每一次獨立，上一次沒做不擋下一次。
7. **每天的事留在開店前檢查**；行事曆不做「每天」重複，「今天」區塊在開店前檢查只顯示、不影響完成狀態。
8. **先只在店內看**；手機每日摘要、Google 日曆同步列第四期，屆時以「系統單向送出」做，不讓外部連進店內。
9. 運費、集運費不攤進商品成本；廠商部分退款不在第一期（作廢原付款、改記淨額）。

## 替代方案

- **全部記在行事曆、不碰採購單**：最單純，但要上架的貨得記兩次，報表也算不到。店主選走採購單。
- **採購單自己記付款（purchasing 內一張付款表），支出另一張**：兩本付款帳，月結同一廠商同時付貨款與運費時要拆兩邊，
  每月支出報表要合併兩個來源、口徑容易分歧。不採用。
- **完整應付帳款（對帳單、沖帳、科目）**：超出單店需求，維護成本高。只做「還欠多少＋付款期限＋結清」。
- **重複待辦預先展開成 N 筆**：要決定展開多遠、改規則要回頭改一堆列；按需建列較簡單。
- **直接用 Google 日曆**：手機提醒好，但跟採購單、付款、庫存連不起來，店員在店裡也看不到全店的事。
  第四期改為單向同步過去，兩邊好處都拿到。
- **允許店員用「取出現金」付廠商**：會放寬既有的現金控管。只開放綁定貨到付款採購單、金額有上限的那一種。

## 影響

- 新 migration：第一期 1A（員工、待辦、事件）、1B（採購單與供應商欄位）、1C（付款、分配、結清、現金異動類型）。
  每段合併後寫 MacBook 升級文件。
- `cashdrawer.expected_amount`、現金報表、現金頁異動清單要認得兩個新類型；CLAUDE.md §7-4 公式文字同步更新。
- 首頁、開店前檢查、導覽列多「今天」與數字；採購頁多日期、付款與月結畫面。
