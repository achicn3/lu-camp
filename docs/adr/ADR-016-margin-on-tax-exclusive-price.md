# ADR-016：目標毛利與毛利率一律對「未稅」售價計

- **Status**: Accepted（2026-08-23）

- **Context**:

  台灣標價含稅（`CLAUDE.md` §6）：`listed_price` / `unit_price` 是客人實際要付的錢，
  發票在總額層級拆一次稅（`split_tax_inclusive`）。這部分沒有爭議。

  有爭議的是「毛利 45%」這句話的分母。原本 §7.9 定義為：

  ```
  建議售價 = round_ntd(收購價 ÷ (1 − margin_pct/100))，為含稅整數元
  ```

  也就是把毛利算在**含稅**售價上。收購頁顯示的毛利率同樣以含稅價為分母。

  問題是那 5% 從來不是店家的錢——它是代國稅局收的，結帳後要繳出去。以含稅價當分母，
  等於把應繳的稅算成自己的毛利：

  ```
  收購 1000、目標毛利 45%
    舊式上架價 = 1000 ÷ 0.55 = 1818（含稅）
    還原未稅   = round(1818 ÷ 1.05) = 1731
    真實毛利   = (1731 − 1000) ÷ 1731 = 42.2%   ← 設 45%，實拿 42%
  ```

  觸發點是 2026-08-22 的店主裁示：收購頁的「估計轉售價」語意是**未稅**（店家實際入袋），
  上架售價才是含稅。若只改估計轉售價那一條路而不動「套用建議」按鈕，同一個欄位的兩顆
  按鈕會用兩種口徑；若連毛利率顯示都不動，按下寫著「目標毛利 45%」的按鈕會得到
  「毛利 42%」的顯示——畫面自己打自己。

- **Decision**:

  1. **目標毛利與毛利率一律對未稅售價計。**
     - `建議未稅售價 = 收購價 ÷ (1 − margin_pct/100)`
     - `建議上架售價（含稅） = round_ntd(建議未稅售價 × (1 + tax_rate))`
     - `毛利率 = (未稅售價 − 收購成本) ÷ 未稅售價`，未稅由含稅價還原，
       與 `split_tax_inclusive` 同式：`round_ntd(含稅 ÷ (1 + tax_rate))`

  2. **全程只四捨五入一次。** 先把未稅取整、再加稅，會多吃一次捨入誤差；
     一律 `round_ntd(未稅 × (1 + tax_rate))` 一次到位。

  3. **`tax_rate` 一律取自 `settings`，不得寫死**（§6）。後端 `suggested_price` 的
     `tax_rate` 為**必填、無預設值**——給預設值就是把 5% 藏進程式碼。前端在設定尚未載入或
     值不可用時**不做換算並明確提示**，不得靜默留空（靜默的後果是店員把未稅價直接打進
     上架售價，每件少收一個稅額）。

  4. **`tax_rate = 0` 時新式退化為舊式**，作為向後相容的檢查點：
     `suggested_price(600, 45, 0) == 1091` 與改版前同值。

  5. **舊資料不回頭改寫。** 已落庫的 `listed_price` 是當時談定的價格，屬既成事實；
     本次只改「下一次按建議鍵會算出什麼」。

- **Consequences**:

  - 同一組輸入的建議售價變高約一個稅額（`收購 1200 / 45%`：2182 → 2291）。
    這不是漲價，是把原本被吃掉的稅補回定價裡。
  - `建議最高收購成本`（`maxAcquisitionCost`）吃的是店員輸入的「估計轉售價」，
    語意改為未稅後，同樣的鑑價直覺會得到**較保守**的收購上限
    （3000 為例：1200 → 1143）。這是刻意的，店家對賣方的出價因此更安全。
  - 公式在系統裡原本有三份：後端 `core/money.suggested_price`、前端
    `features/acquisition/pricing.ts`、以及 `qa_e2e/sim_helpers.py` 自抄的一份。
    本次把第三份刪除、改 import 後端那份，收斂成兩份（後端權威 + 前端鏡射）。
    模擬器的稅率改由該店 `settings` 讀取，不在腳本裡寫死。
  - **前端鏡射必須逐值等於後端**：`cost ÷ (1 − m/100)` 這半原本仍是浮點除法，
    剛好落在 .5 的商會算成 …49999999 而少一元（審查實測：cost 1–3000 × margin 0–99 ×
    稅率 0.05，有 2.76% 的組合與後端差 1 元，且**一律偏低**）。已改為全程整數比值
    `round(cost × 100 × (10000 + bp) ÷ ((100 − m) × 10000))`，與後端 `Decimal` 對齊。
  - **尚未收斂的一處**：報表的 `gross_margin_rate`
    （`backend/app/modules/sales/service.py`）分母仍是含稅營收，
    與收購頁會差約 2.6 個百分點（收購 1000／上架 1909：收購頁 45%、報表 47.62%）。
    列為後續 task，見下。
  - 後端 `core/money.suggested_price` 與 `InventoryService.suggested_listed_price`
    目前沒有任何端點呼叫（建議價完全在前端算）。**刻意保留**：它是「規格在程式裡的
    可執行樣子」，並由測試釘住；刪掉的話 §7.9 就只剩散文。

- **Follow-ups**（各自獨立 task，不併入本次）:

  1. 報表 `margin_breakdown` 的毛利率改以未稅營收為分母（R2／R5／R6 共用口徑）。
     報表為即時計算、無彙總表，不需 migration。
  2. 寄售抽成與應付改以未稅價計（店主 2026-08-23 裁示：店家不代寄售人吸收 5% 稅），
     牽動 `CLAUDE.md` §7.2 核心不變量、`consignment` service、撥款頁 UI 與報表。
  3. 散裝「每件均一價」比照序號品標示含稅並提供未稅→含稅換算
     （`bulk_lots.unit_price` 在 POS 同樣被當含稅單價）。
     本次一併**刪除**了前端的 `suggestedBulkUnitPrice`——它在 `main` 上就沒有任何呼叫端，
     替死碼加參數與測試只是在維護沒人用的東西（§9）。散裝 UI 真的接上時再引入。

- **Alternatives considered**:

  - **維持含稅口徑、只改文案說明**：無法解決「按 45% 得到 42%」的矛盾，
    也不能讓店主真的拿到他要的毛利。
  - **由後端開端點供前端取建議價**：只為了一個除法做網路往返，過度工程；
    且離線/慢網時收購頁會卡住。維持前端計算、後端保留同式作為規格對照。
  - **讓 `tax_rate` 有預設值 0.05**：違反 §6，且設定讀取失敗時會靜默用錯的稅率算價，
    比明確報錯更危險。
