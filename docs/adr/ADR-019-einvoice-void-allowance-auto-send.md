# ADR-019：發票作廢／折讓自動送出，開立維持人工

- **Status**: Accepted（2026-08-27）

- **Context**:

  電子發票有三種要送交平台（Amego）的訊息：開立 `F0401`、作廢 `F0501`、折讓 `G0401`。
  只有開立會被送出——`EInvoiceService.issue_for_sale` 在 POS 結帳後**同步**呼叫
  `send_via_amego`。作廢與折讓只被排進 `einvoice_upload_queue`，然後：

  - 後端啟動（`app/main.py` lifespan）只跑備份與客顯兩個排程，**沒有發票佇列的**；
  - 前端只呼叫四支發票端點（issue／manual-invoice／proof-printed／reprint-payload），
    `/einvoice/queue`、`/queue/{id}/send`、`/queue/{id}/retry` **一支都沒接**。

  文件對此自相矛盾：`docs/34` §「作廢要先送出才看得到」說「實際送出是店長在發票佇列
  手動觸發」，而 `docs/36` §95/97 明載「不另建發票佇列頁」「前端沒有任何發票佇列頁面」。
  設計預期的那個人工入口從未存在。

  **實測後果**（2026-08-27，`lucamp_manual`）：批次作廢 25 張已開立發票後，28 筆 F0501
  全部停在 PENDING、`attempts=0`；向 Amego 逐張查證，那些發票在平台上
  `invoice_status=99`（完成）、`cancel_date=0`——**帳上作廢、平台有效**。客人手上那張仍可
  兌獎，申報營業額對不起來，且沒有任何畫面會提醒。

  這類缺陷全量帳務稽核抓不到：「發票 VOID_PENDING ＋ 佇列 PENDING」本身完全自洽，
  它就是「等待送出」的正確長相。要發現它必須走出系統去問平台。

- **Decision**:

  1. **新增背景自動送出**（`einvoice/background_service.py` + `scheduler.py`，60 秒 tick），
     比照既有客顯排程。傳輸完全委派既有的 `send_via_amego`——認領、CAS 重取鎖、
     凍結 payload、對帳先行等保護一律沿用，本層不重寫任何傳輸邏輯。

  2. **自動送出只涵蓋作廢與折讓，不含開立**（`AUTO_SEND_ACTIONS`）。理由有二：
     - 開立牽涉字軌配號與客人當下要拿到的發票，事後自動補開可能在客人離店後才成立；
     - 佇列可能積著大量歷史待開立列（本店實測 17,692 筆模擬資料殘留），無差別排空
       等於把一整年的舊發票補開到平台上——那不是修好，是把問題放大一萬倍。
     開立的補救走人工（發票待處理頁的「重新開立」），由店長決定。

  3. **年齡上限 7 天**：更舊的待送出多半是資料殘留或另有內情，自動補送風險大於效益。

  4. **退避只套在重試**：已認領（`xml_path` 有值＝曾嘗試）者隔 5 分鐘再試，避免連續
     重擊平台；**從未嘗試過的下一輪就送**——那段等待期間平台上那張發票仍然有效，
     為退避而白等只是把風險窗口拉長。

  5. **新增發票待處理頁**（`/einvoice-queue`，MANAGER）：待送出／平台退回一覽，
     可「立即送出」「重試」「重新開立」。導覽列**只以平台退回筆數**顯示紅點——
     待送出的多半下一輪就送掉了，拿它當紅點會天天亮著，店員很快就學會無視。

  6. **開立類的送出要二次確認**，對話框寫明交易編號與日期。實測踩過：煙霧測試盲按
     待送出清單第一列，替一筆三天前的舊交易補開了一張真發票。作廢與折讓不需確認——
     它們只是把「已經作廢」這個既成事實補送出去，不會憑空產生新單據。

  7. **作廢成功的提示改為明講後續**：「發票作廢申請已送出，系統會在數分鐘內完成平台
     作廢；在那之前客人手上那張發票仍為有效。」店員需要知道那張紙還有效多久。

- **Consequences**:

  - 上線後積壓的 28 筆作廢全部自動送出；向平台複查，先前 `C0401`（開立）的發票
    已變為 `C0501`（作廢）。
  - `GET /einvoice/queue` 回應新增 `invoice_no`／`sale_id`／`total`：內部 id 對店長毫無
    意義，沒有這三個欄位那一頁沒辦法用。屬 API 合約變更，生成物已同步更新。
  - `build_amego_client` 由 router 抽到 service 供兩處共用（原本 router 自己一份，
    背景送出再組一份必然在憑證來源或 base_url 上漂移）。
  - **開立失敗仍不自動重試**（店主 2026-08-27 裁示）。`/sales` 對 `PENDING_ISSUE` 的單
    原本只有「登記手開發票」一顆按鈕，等於只剩紙本一條路；現在發票待處理頁補上
    「重新開立」，兌現 POS 對店員說過的「可稍後補開」。
  - 該端點**冪等且對帳先行**：送出去但回應中斷的那種，再按一次會先向平台求證、
    認回原發票，不會重複開立。故店員不需要自己判斷「到底開出去沒」。

- **Alternatives considered**:

  - **無差別排空整個佇列**：會把 17,692 筆歷史待開立補開到平台。已由測試明確禁止。
  - **開立也自動重試**：少一次人工，但要接受「發票可能在客人早已離店後才開出來」；
    店主裁示不要。
  - **只做佇列頁、不做自動送出**：店員不會主動去看沒有紅點的頁面，而紅點要能亮起來
    本身就得先有人去送——等於把「會不會送」這件事賭在人記不記得。
  - **維持現狀、只改文件**：作廢在平台上不成立是稅務問題，不是說明問題。
