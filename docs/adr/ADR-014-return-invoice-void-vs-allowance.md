# ADR-014：退貨時的發票處置——同月整筆退作廢、其餘折讓

- **Status**: Accepted（2026-08-01 店主裁示；接續 [ADR-013](ADR-013-sale-and-invoice-lifecycle-separation.md)「變更 B」）。

## Context

原本**所有**退貨（含整筆退貨）一律開折讓單（G0401）。店主指出這不符會計實務：當月、尚未申報的
發票整筆退貨，應收回發票證明聯並**作廢**（F0501），折讓是不得已才用的手段。

法規與實務依據：

- **《統一發票使用辦法》第 20 條**：銷貨退回時，**銷售額尚未申報**者，買受人為非營業人時
  「應收回原開立統一發票收執聯……並註明作廢」；**已申報**者則取得折讓證明單（同法 §20-1）。
- **《電子發票實施作業要點》第 9 點**：電子發票的**開立、更正、作廢、銷貨退回或折讓，
  應經買受人同意**，證明文件保存 5 年。
- 光貿（Amego）FAQ 的實務口徑：**當月**的用作廢、**跨月**的用折讓、跨期已申報一定折讓。

系統無從得知「何時申報」（申報是人在國稅局端做的事）。

## Decision

1. **代理判準**：以「原發票開立日與退貨日是否落在**同一台北曆月**」代替「是否已申報」。
   店主確認本店不會在當月提前申報，故同月＝尚未申報。判斷邏輯集中在
   `backend/app/modules/returns/invoice_policy.py`（純函式、無 DB，可完整測試）。
2. **決策順序**（`decide()`，順序本身是規格）：
   1. 無發票／發票尚未開立成功 → `NONE`（不做任何稅務動作）
   2. 原發票**有作廢在途**（結果未確認）→ `REVIEW_REQUIRED`，轉人工，不得疊加
   3. 原發票**已有折讓**（已核可**或在途**）→ `ALLOWANCE`，**永遠不得再作廢原發票**
   4. 非累計全退 → `ALLOWANCE`
   5. 跨月 → `ALLOWANCE`
   6. 其餘（同月＋累計全退）→ `VOID`，`requires_paper_recall = 有紙本證明聯`
3. **部分退貨一律折讓，且不得要求收回紙本**——原發票對未退商品仍是客人的購買憑證。
4. **未收回紙本 → 拒絕整筆退貨退款**（店主裁示）。這不是技術限制而是商業政策：作廢需要
   收執聯，收不回來就不能作廢，店主選擇不讓步。載具／捐贈發票沒有紙本，不受此限。
5. **折讓與作廢皆須買受人簽名同意**（作業要點第 9 點）。同意以顧客螢幕簽署任務
   `RETURN_INVOICE_CONSENT` 留證，退貨成立時一次性 `CONSUMED`。
6. **同意的內容由後端重建、範圍與退貨綁定**：客端只能指定「退哪些明細、退幾件」，金額、
   發票號碼與處置方式一律由後端依銷售單與政策重算後寫入快照；退貨成立時再比對
   `content.return_lines` 與實際退貨範圍，不符即拒絕。否則同意書等同空白支票。
7. **買受人可以是非會員**：`signature_tasks.contact_id` 放寬為可空，並以 CHECK 限縮
   「只有 `RETURN_INVOICE_CONSENT` 可為 NULL」。零售退貨多半是臨櫃客人，若強制綁會員，
   等於讓所有匿名交易的已開發票退貨全部無法完成。
8. **退貨預覽 API**（`POST /returns/preview`，`previewReturn`）：店員勾選品項後、送出前
   先問後端「這次會怎麼處理發票」。**不可**放在 sale detail——店員尚未選定退哪些品項時，
   後端無從得知是否構成累計全退。預覽僅供提示，送出時後端會以當下狀態**重新判斷一次**。

## Alternatives

- **一律折讓（維持現狀）**：駁回。省事但不符會計實務，也不是店主要的。
- **讓店員自己選作廢或折讓**：駁回。規則是法定的、可由系統判定；交給店員選只會產生
  不一致的帳務，且出錯時無從追究依據。
- **未收回紙本就改開折讓**：駁回（店主裁示）。等於用折讓迴避「應收回」的義務。
- **把判斷放在 sale detail 回應**：駁回（見 Decision 8）。

## Consequences

- 退貨對話框新增「發票處置」區塊：說明會作廢或折讓、必要時要求勾選收回紙本、推送簽名同意。
- 三處必須用同一份退貨明細（預覽、同意任務、送出退貨），畫面以同一個 `returnLines` 供應，
  並以計畫指紋讓「改了要退什麼」自動失效先前的勾選與簽名。
- `invoice.void_reason` 得以區分 `SALE_VOID`（打錯單）與 `FULL_RETURN`（有效交易全退）。

## 已知待辦

1. 作廢／折讓送 Amego 後的「結果未知」目前以佇列 PENDING＋已認領隱含表達，缺顯式狀態
   （承 ADR-013 待辦 3）。`REVIEW_REQUIRED` 已能擋下疊加，但 UI 尚無專門的對帳畫面。
2. 「同月＝未申報」是代理判準。若日後改為當月提前申報，此規則必須同步調整（目前以
   `invoice_policy.py` 的模組 docstring 明載此前提）。
