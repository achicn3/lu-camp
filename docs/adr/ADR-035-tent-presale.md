# ADR-035：寄售帳篷預售——同一張官網資料表，序號品可晚到

- 狀態：已採納（店主七項裁示 2026-10-31；規格見 docs/102）
- 相關：ADR-033（寄售帳篷上官網）

## 背景

店主要讓帳篷還在賣家家裡時就先上官網賣（賣家用 Google 表單登記，不收身分證）。
現行官網資料（`online_tent_listings`）綁在序號品上，而序號品只能經收購建立、收購規定對象必須有身分證。

## 決定

1. **不放寬收購的身分證規定**。預售不是收購，不建序號品、不建寄售人；身分證照舊在到店辦寄售時收。
2. **預售跟現貨共用 `online_tent_listings`**：`serialized_item_id` 改可為 NULL，預售列另存品牌／名稱／售價／賣家聯絡方式
   （presale_*）。照片、缺件、瑕疵、影片、上架、保留的編輯、推送、雲端都直接沿用，不必另做一套。
3. **到店轉寄售走收購頁**：寄售鑑價列帶選填的 `presale_listing_id`，收購服務在同一交易內呼叫 onlineorder 服務把預售接上新序號品；
   接不上就整張寄售單失敗（不留下「寄售成功、官網沒接上」的半套狀態）。
4. 官網 `id` 從預售編號換成序號品編號，feed 帶 `formerIds` 讓舊網址轉址；雲端不改。

## 替代方案

- **收購新增「表單來源」、身分證選填**：要動身分證必填、切結簽署綁身分證指紋等不變量，風險大；預售階段也根本還沒收到東西。不採。
- **預售另開一張表、轉換時搬資料**：照片、推送都要重做或搬移，轉換時容易漏欄位。不採。
- **先建一個「待收」序號品**：會出現在庫存、POS 掃得到、報表算進去，與「還沒收到東西」不符。不採。

## 影響

- 新 migration：`online_tent_listings` 欄位與 CHECK 變更；降版時若有預售列（serialized_item_id 為 NULL）拒絕降版。
- 收購 API 多一個選填欄位，不帶時行為不變；需更新 OpenAPI 生成物。
- 官網 repo（`~/lukeng-homepage`）同步改 tents.js 顯示預售。
