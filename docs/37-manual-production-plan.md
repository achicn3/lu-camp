## 2. 四個必須先解決的衝突

裁示彼此組合後產生的矛盾，先在此定案，避免執行到一半才發現。

### 2.1 大量資料 × 真發票

15,000 筆銷售若都開發票，等於送 15,000 張真發票到 Amego 測試環境——不可行也不該做。

**定案**：
- **P0 大量資料在 `einvoice_enabled = false` 下產生**，發票狀態一律 `NOT_ISSUED`
- 只有**手冊腳本要示範的少數幾筆**，由腳本**自行以 `withSettings` 暫時開啟再還原**
- 這符合 `CLAUDE.md §6`：不論開關，每一筆銷售都完整寫入 `sales`；開關只決定是否產生電子發票

> **絕對不要手動 PATCH 設定把 `einvoice_enabled` 開著**（審查 critical）。三支既有腳本
> （`09c-invoice-return-void`、`09d-invoice-disposition`、`17-einvoice-linepay`）開頭就會檢查，
> 發現全域已啟用即 **`throw`「疑似正式環境，中止」**，整輪當場停住。
> 反向也會壞：`08c-pos-consignment` 要截「未啟用電子發票時的提示」（`.pos-invoice-off`，
> 手冊圖 7-19），全域開著時該元素不存在，`makeShot` 會逾時或截到錯的畫面。
> 既有機制是 `_lib.mjs` 的 `withSettings(["einvoice_enabled"], …)`——沿用它，不要另闢蹊徑。

### 2.2 今日交易 × 「尚未開帳」畫面

原始指令 §3.3 要求今日有交易（儀表板不為空）；但今日有現金交易就必須開帳，而手冊腳本 `02-cash-open` 要示範**開帳**畫面（需「尚未開帳」狀態）。

**定案**：seed 今日交易後**把當日班別結掉**。今日資料留著、抽屜是關的，兩邊都成立。
（`docs/34` 已記載 `seed_dev_consignment` 有同樣問題，處置方式一致。）

### 2.3 平台識別碼碰撞（**必踩，已實測確認**）

送到 Amego 的識別碼由本地流水號推導：發票 `S{store}-{sale_id}`、折讓單 `L{store}-{allowance_id}`。
重建資料庫後編號從 1 重來，會撞上前幾輪重跑留在平台上的舊資料。實測結果：

| 識別碼 | 平台狀態 |
|---|---|
| `S1-1` | 已存在（ZA10018786，2026-07-23，$400） |
| `S1-14` | 已存在（ZA10028313，2026-08-03，$270） |
| `S1-20`、`S1-50` | 已存在 |
| `L1-1`、`L1-2` | 折讓單已存在 |

撞號的症狀是「對帳先行」查到舊發票 → 金額或時間對不上 → 判定結果不明 → **開立卡住**（502）。

**好消息：訊息會明講。** `amego.py` 的兩道守衛分別回
「…不符——**該紀錄可能不是本筆（識別碼重號）**，待人工對帳」與
「…**該紀錄是還原前的舊資料（識別碼重號）**，待人工對帳」。
看到「識別碼重號」就是這個問題，不必懷疑平台故障——**此句值得寫進手冊 FAQ**。

**定案**：migration 之後、seed 之前執行

```sql
ALTER SEQUENCE sales_id_seq RESTART WITH 300000;
ALTER SEQUENCE invoice_allowances_id_seq RESTART WITH 300000;
```

執行當天**先掃一次號段**確認未被佔用（Amego 測試帳號是公開共用的，別人也會用）。

**副作用**：restart 後銷售單號從 300001 起（六位數）。`docs/34 §5` 的
「訂單編號 `S1-14` = 銷售 #14」範例與既有手冊圖說的小號碼會全部過時，需同步更新。
另已查證**沒有第三個**由本地流水號推導的平台識別碼——LINE Pay 的 orderId 來自
（store, 冪等鍵, 金額），不受影響。

## 4. 角色（三種，完整寫）

| 角色 | 說明 | 手冊處理 |
|---|---|---|
| `MANAGER` | 管理者。可跨店彙整、解密 PII，並獨佔多項敏感動作 | 正文主視角 |
| `CLERK` | 門市店員。日常結帳、收購、退貨 | 每個 MANAGER-only 動作標「限店長」，並以 `dev-clerk` 截一組對照圖 |

**判定方法必須三向交叉**（只看 `ManagerDep` 會漏；審查 high）：

1. `ManagerDep` 相依
2. 全域 grep 內聯判定 `UserRole.MANAGER.value`——有三處店長閘門**不是** `ManagerDep`：
   `returns/router.py`（手開紙本處置確認）、`contacts/router.py`（national_id／roles）、
   `inventory/router.py`（`_ensure_category_create_allowed`，條件式）。
   **`sales/router.py` 沒有內聯判定**——它的同名 `manual_paper_disposed` 掛在
   `/sales/{id}/void`，而該端點本來就是 `ManagerDep`（複審更正）。
3. 前端的 `managerOnly` **有兩份且不一致**：導覽（`app/(authed)/layout.tsx`）與
   首頁模組卡片（`app/(authed)/page.tsx`）。例如「備份」在導覽是 managerOnly，
   首頁清單根本沒有這一項。兩份都要比對。

**MANAGER-only 動作清單**（實作時再核一次）：
作廢銷售、作廢收購、改售價、現金手動調整、查看身分證、門市活動、餐飲菜單、報表、設定、
備份、發票佇列操作、**登記手開發票**、**手開紙本處置確認**、購物金人工校正、
庫存「詳細」（序號品／一般商品／散裝批）、分類目標毛利率與分類定價規則、
贈品／折扣原因代碼維護、簽名 PNG 待清理報表、LINE Pay 退款對帳與裁定、客顯付款對帳、溢價率歷史。

### 7.2.1 相依鏈：**產生順序不能任選**（店主提醒 2026-08-19）

各模組彼此有相依，順序錯了不是資料難看，是**根本產不出來或產出假資料**。
以下每一條都查證自程式碼實際的守衛，不是推測：

```
聯絡人（會員/賣方）
   └─► 收購（買斷/寄售/散裝）──► 庫存（序號品/散裝批/一般商品）
                                      │
現金班別（必須開帳中）──────────────────┼──► 銷售 ──► 寄售結算（PENDING）
   ▲                                   │                    │
   └── 收購付現、寄售付款也要開帳中 ─────┘                    └─► 付款（PAID）
                                        └──► 退貨 ──► 折讓/作廢（僅已開票者）
顧客螢幕配對 ──► 簽名任務 ──► 被單據 CONSUMED
```

**硬性前置（違反即拋例外，不是警告）**：

| 動作 | 前置 | 依據 |
|---|---|---|
| 結帳收現 | 開帳中的 `cash_session` | `sales/service.py`「結帳收現必須在開帳中…」 |
| 收購付現 | 同上 | `acquisition/service.py:521` |
| 作廢付現收購的退款 | 同上 | `acquisition/service.py:664` |
| 寄售付款 | 同上（`record_movement` 內擋） | `consignment/service.py` |
| 賣出寄售品 | 該序號品存在且為寄售 | 售出時才建 `PENDING` 結算 |
| 寄售付款 | 先有 `PENDING` 結算 | 結算由「賣出」產生，不能憑空建 |
| 含餐飲的單 | 必須宣告內用/外帶（＋內用要桌號） | `_validate_service_mode_shape` |
| 內用桌號 | 桌號須在 `settings.dine_in_tables` 內 | 否則 `InvalidServiceMode` |
| 退貨折讓/作廢 | 原發票已開立 ＋ 客人簽名同意（＋整筆退要收回紙本） | `returns/invoice_policy.py` |
| 簽名任務 | 已配對的顧客螢幕（KIOSK） | `signing` 走 `KioskMutationDep` |

**因此 P0 的建置順序固定為**：

1. 聯絡人（會員／賣方／寄售主）
2. 商品來源：收購（買斷/寄售/散裝）＋ 採購收貨（一般商品）
3. **開一個當日班別** → 產生該日銷售 → **結掉班別**（每個歷史營業日重複）
4. 寄售品售出後才有 `PENDING` 結算 → 再產生付款（PAID/部分留 PENDING）
5. 退貨（依政策分流折讓/作廢；餐飲不可退）
6. 簽名任務（需先配對顧客螢幕）

**時間序的陷阱**：既有 `seed_dev_demo` 只開**一個**班別、全部銷售掛其下再回填
`created_at`。§7.4 要 305–400 個**歷史班別**，且 §7.5 #4 的現金等式要 **per-session**
驗證——這一項**不能沿用**既有手法，必須逐日開帳/結帳並把該日銷售掛在對應班別下。

### 7.3 時間軸與營運節奏

- 涵蓋**最近 12 個月至今日**，含**今日的部分交易**（今日班別最後要結掉，見 §2.2）
- 營業日約 305 天；農曆春節連休 4–5 天；另 2–3 個颱風休業日
- **季節性（台灣露營）**：裝備類 10 月–翌年 2 月旺季，6–8 月淡季（約旺季 40%）；飲品夏季反向上升
- **收購來源季節性**：3–5 月（露季結束出清）與 1 月（年前整理）為送件高峰
- **週間**：週六日約平日 2.5–3 倍
- **時段**：飲品上午小高峰；裝備 14:00–18:00，假日 13:00–17:00 尖峰

### 7.4.1 銷售量的來源必須混合——只賣序號品達不到目標

§7.4 的三個數字互相夾擠，實作前先算清楚：

```
收購總量 ≈ 已售序號品 + 期末在庫
9,000    ≈ 已售        + 1,100     →  序號品最多貢獻約 7,900 筆銷售
```

但目標是 **12,000–15,000 筆銷售**。差額約 5,600 筆**必須**來自
「不扣庫存或可重複販售」的品項：

| 來源 | 特性 | 約略筆數 |
|---|---|---|
| 餐飲（`MENU`） | 現做、不扣庫存，可無限賣 | 2,500 |
| 一般商品（`CATALOG`） | 可採購補貨 | 2,000 |
| 散裝批（`BULK_LOT`） | 一堆可分次賣 | 1,100 |

**這解釋了為什麼 §7.4 會同時列出「新品 SKU 60–120」「飲品/餐點 SKU 25–40」
「散裝批 150–250」——它們不是裝飾，是銷售量的主要來源。**
只賣序號品的話，銷售筆數的天花板等於收購量，永遠達不到目標。

（實測：只賣序號品時，`--per-day 20` 跑滿 305 天也只有約 6,600 筆。）

### 7.4.2 三個坑：單 vs 件、相位相反的季節性、從零起跑

實作到一半才發現的，記在這裡避免重蹈。

**① 「買斷收購 1,800–2,400」數的是「單」，「二手商品個體 8,000–10,000」數的是「件」。**
約 3.3 件/單。一單一件的話兩個目標**不可能同時成立**。現實也是如此——
客人多半一次拿一整袋來賣，不會一件一趟。

**② 收購與銷售的季節性相位相反，會把貨架抽乾。**
客人**春天**露季結束才出清送件，客人**冬天**才買裝備。若照這個相位直接模擬，
10–2 月的旺季會把庫存吃光——實測跑到 10 月時在庫只剩 **35 件**。
真實店家在旺季前會**主動去調貨**，故收購季節性的秋冬底線要拉高、峰谷比要壓平。

**③ 從零庫存起跑不真實，須有暖身期。**
報表視窗開始的那一天，店裡本來就有前幾個月累積的存貨。`--warmup-days`（預設 150）
在視窗前先營運一段時間；**其產出分開計數**——§7.4 的目標談的是 12 個月視窗，
把暖身期混進去會讓「達標」變成假的。

**期末在庫實測 1,816 件，高於 §7.4 的 900–1,300——但這不是校準沒調好。**

把 12 個月的月末在庫還原出來就看得很清楚：

| 月 | 08 | 09 | 10 | 11 | 12 | 01 | 02 | 03 | 04 | 05 | 06 | 07 | 08 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 月末在庫 | 1336 | 1359 | 1143 | 758 | 498 | **428** | 451 | 693 | 1068 | 1368 | 1564 | 1725 | **1816** |

**視窗的結束點正好落在季節高峰。** 春天客人出清送件、夏天裝備賣得慢，八月的倉庫本來
就是最滿的；十二月到二月則是全年最低（428 件）。全年平均約 1,100 件，正在區間內。

要把八月的 1,816 壓到 1,300，就得整條曲線下移 500 件——一月的低點會變成 **0**，
也就是整個冬天旺季貨架空著。空貨架是模型假象、不是真實店家。

**§7.4 的 900–1,300 是在沒考慮「量測點落在季節高峰」的前提下寫的。**
建議口徑改為「全年平均 900–1,300」，或明確指出量測日期。

### 7.4.3 時間序回填：同一個錯誤犯了四次

service 一律以 `now()` 落地時間欄，而報表依時間篩選。**漏回填任何一個欄位，
資料就整批擠在今天，而「數量達標」的綠燈完全看不出來**——要另外去開那張報表才會發現。

| # | 漏掉的欄位 | 症狀 |
|---|---|---|
| 1 | `cash_sessions.opened_at` / `closed_at` | 305 個班別全擠在今天，現金對帳報表失真 |
| 2 | `acquisitions.created_at` | 整年的收購都落在今天 |
| 3 | `consignment_settlements.created_at` | 「賣出滿 7 天才來領錢」永遠不成立，已付款數 **0** |
| 4 | `serialized_items.intake_date` / `bulk_lots.intake_date` | **滯銷庫存報表整頁空白** |

第 4 個特別隱蔽：`created_at` 回填了也沒用，**滯銷報表看的是 `intake_date`**。

**護欄**：`verify_invariants()` 的「時間序已回填」對五張表檢查其時間欄，
單日佔比超過三成即失敗。護欄本身要**對著已知有問題的資料驗過**才算數。

### 7.4.4 期末在庫必須含滯銷品，否則要另外製造

`intake_date` 修好之後，「滯銷 180 天以上」仍是 **0 件**——因為模型裡每一件終究
都會被賣掉，期末在庫必然全是近期入庫的。真實店家一定有賣不掉的東西
（開價過高、款式冷門、有使用痕跡）。

作法：入庫時把約 7% 歸為**滯銷品**、另池存放，不隨主池游標被依序賣掉；
仍有 2% 機率被選中（有人識貨、或降價出清），但會一直留在架上變老。
`--slow-mover-pct` 可調。

### 7.4.6 用詞審核：截圖裡的每一句話，一般人要看得懂（店主裁示 2026-08-20）

**審核每張截圖時一併檢查畫面上的文字**，不只是版面與數字。標準是「沒學過這套系統的
新店員，第一次看就懂」。

**這件事要在截圖之前做完。** 等截完才發現用詞太專業，整批要重拍。

要抓的四類：

| 類別 | 例子（實際掃到的） | 問題 |
|---|---|---|
| **程式常數外洩** | `PAYMENT_UNCERTAIN：本筆付款結果尚未裁定…` | 店員看不懂大寫英文代碼 |
| **技術名詞** | 「簽名 **PNG** 保存天數」 | PNG 是檔案格式，店員只知道「簽名圖檔」 |
| **書面語／法律腔** | 「尚未**裁定**」「留存為失敗**證據**」 | 讀起來像公文，不像店裡講的話 |
| **語句不通順** | 「已還原**原原**送出內容」 | 疊字、贅字、斷句怪 |
| **非必要的英文** | 「一般商品 **SKU**」「**POS** 櫃檯」 | 有現成的中文說法就用中文 |
| **不常用的詞** | 「逾時」「清場」「留痕」「裁定」 | 書面語，店裡不會這樣講 |

**英文的判準是「有沒有必要」**，不是一律禁：

### 7.4.8 真的送上 Amego（測試環境）

`app/scripts/seed_issue_invoices.py`，與 seed 分開執行。**跑這支就是真的在開發票。**

**四道守衛**（都實測過會擋）：`APP_ENV`、`ALLOW_DEV_SEED`、資料庫名白名單，以及最重要的
**賣方統編必須是 Amego 測試統編 `12345678`**——正式統編跑下去就是對國稅局開出上萬張
不存在的交易，不可回復。

實測（2026-08-20）：**17,543 張真的開立**、24 分鐘、併發 8、失敗 0.19%。

#### 平台單號的號段一定要隔開

單號由本地 id 導出（`OrderId = S{store}-{sale}`），測試環境又是**官方公開共用帳號**，
所以低號早被用掉。`seed_demo` 會先把 `sales_id_seq` 推到一個高起點。

**起點必須是隨機的，不能用 epoch 秒**——這是實作時踩過的坑：epoch 一秒只走 1，
但一次 seed 在 16 分鐘內吃掉近 18,000 個 id，**兩次執行間隔不到 5 小時就會重疊**。
症狀是重建資料庫重跑之後，開頭 29 筆全部撞上前一次已開立的發票。

#### 撞號是被「對帳先行」抓出來的

錯誤訊息是「invoice_query 查到的含稅總額 320 與本地 400 不符——該紀錄可能不是本筆
（識別碼重號），待人工對帳」。直接向平台查證，回的是**同一個 order_id、不同金額**——
真的撞號，不是誤判。

**若沒有這道守衛，會把別人（或自己上一次）的發票號碼補記成本店的。**
這是整套發票流程裡最值得留著的一道檢查。

#### 剩下的 29 筆刻意不清掉

它們卡在「待人工對帳」——那正是系統設計要處理的狀態，也是真實店家會遇到的情形
（平台答案不明、需人工查證）。留著讓手冊的對帳畫面有東西可示範，比清成全綠更有用。

客人碼」，真店面用掃碼槍讀客人手機），只能從沙盒頁的條碼圖解出來，每筆要重載一次頁面。
數十筆足夠覆蓋畫面與報表；上千筆沒有意義。

#### 兩個「同 session」合約

`BackupService.run_backup` 與 `RestoreService.run_restore` 都是同 session 版本，
**呼叫端要自己 commit**。少了那行，R2 上的物件是真的、也印出 SUCCEEDED，
但 `backup_runs` 那一列會隨 session 關閉被丟掉。第一次就這樣「成功」了卻沒有紀錄。

#### 待修：備份修剪的前綴比對範圍過寬（產品缺陷，非 seed 問題）

`_prune_remote` 以 `backups/{db_name}_` 為前綴列出物件並刪除不在保留清單內的，
但保留清單 `newest_succeeded_r2_keys` 是**精確**比對 `BackupRun.db_name == db_name`。

兩者不對稱：備份**正式庫 `lucamp`** 時，前綴 `backups/lucamp_` 會一併列出
`lucamp_sim_*`、`lucamp_e2e_*`、`lucamp_manual_*`，而這些都不在保留清單裡 → **全被刪除**。

目前 bucket 裡只有測試備份，損失有限；但只要出現「一個庫名是另一個庫名的前綴」
（例如日後有 `lucamp` 與 `lucamp_archive`），就會刪掉不該刪的。
**修法**：比對時要求前綴之後緊接時戳格式，而非任意字元。

## 11. PE：電子發票模組驗收（對真平台，排在 P2 之前）

店主裁示：**發票相關 API 要全部測過**。本階段獨立於手冊產製，先確認模組行為，
再據以撰寫手冊。

### 11.1 為什麼要獨立一步

盤點既有腳本後發現一個空白：**沒有任何腳本呼叫過 `POST /einvoice/queue/{id}/send`**
——也就是作廢（F0501）與折讓（G0401）的送出路徑，**自動化覆蓋為零**。

（更正：不是「從未走過平台」。`docs/current-status.md` 記載 2026-07-23 已有一張真 F0401
與**兩張 G0401** 走完平台，手冊也收錄了 Amego 後台的作廢發票圖。當時是店長手動以 curl
打 `send`——Amego 後台只能看，不能送。）手冊要描述這兩條流程，就不能只靠一次人工紀錄。

### 11.2 API 面清單（查證自 `einvoice/router.py`、`einvoice/amego.py`）

**HTTP 端點（6 支）**

| 端點 | 用途 | 既有覆蓋 |
|---|---|---|
| `GET /einvoice/queue` | 佇列列表（狀態過濾、分頁） | 已被讀取驗證 |
| `POST /einvoice/sales/{id}/issue` | 開立（冪等） | B2C／載具／B2B 已對真平台驗過 |
| `POST /einvoice/sales/{id}/manual-invoice` | 手開紙本登記 | 有腳本，**未對真平台**驗證 |
| `POST /einvoice/queue/{id}/send` | 送出（ISSUE／VOID／ALLOWANCE 共用出口） | **無** |
| `POST /einvoice/queue/{id}/retry` | 重試（FAILED → PENDING） | **無** |
| `POST /einvoice/queue/{id}/result` | 記錄回執 | **無** |

**平台端點（5 支）**：`/json/f0401`、`/json/f0501`、`/json/g0401`、
`/json/invoice_query`、`/json/allowance_query`。後三者除了「開立前對帳先行」之外，
沒有針對性驗證。

**開立變體（4 種，由 `build_f0401_data` 分支決定）**：
B2C 一般（`BuyerIdentifier=0000000000`、`TaxAmount=0`）、B2B 統編（用發票落地快照的
net/tax 分稅）、手機載具（`CarrierType`／`CarrierId1`／`CarrierId2`）、捐贈（`NPOBAN`）。
**捐贈那條只在 UI 欄位出現過，從未真的開出一張捐贈發票。**

### 11.3 驗收矩陣（`frontend/scripts/einvoice-acceptance.mjs`）

比照既有的 `linepay-acceptance.mjs`（同樣是「對真平台把一個整合的 API 走完」）。
以 API 為主、不走瀏覽器——UI 部分既有 `einvoice-smoke.mjs` 已覆蓋。

1. **開立四變體**：B2C／B2B／載具／捐贈，各取得號碼與隨機碼
2. **冪等**：對同一筆再呼叫 `issue`，必須回原發票且**不得**再送平台
3. **對帳先行**：以 `invoice_query` by `order_id` 查得到剛開的那張，金額相符
4. **作廢**：同月整筆退貨 → 排 F0501 → **真的 send** →
   以 `invoice_query` by `invoice_number` 確認平台狀態為已作廢
5. **折讓**：部分退貨 → 排 G0401 → **真的 send** →
   以 `allowance_query` 確認折讓單存在，且折讓單號、原發票號、稅額與含稅總計相符
6. **已折讓後再退貨** → 必須繼續折讓，**不得**作廢原發票
7. **佇列端點**：`retry`（FAILED → PENDING）、`result`（記錄回執）
8. **手開紙本**：登記後 ISSUE 佇列轉 `CANCELLED`；三個出口（F0501／G0401／退貨決策）
   全部擋下；並以 `invoice_query` 確認**平台上真的沒有那張**
9. **銷售作廢** → 連動發票作廢

每一步保留平台回應的原始碼與號碼，作為證據鏈輸出。

### 11.3.1 這些查證要怎麼做（沒有現成端點）

`invoice_query`／`allowance_query` **只存在於後端 service 內部的「對帳先行」，沒有對外端點**。
所以第 3、4、5、8 項的平台查證**不能靠打自家 API**。

**定案**：平台查證以 `backend/` 下的一次性 Python 腳本執行，直接重用既有 `AmegoClient`
（簽章、`x-www-form-urlencoded`、`md5(data+time+app_key)` 都已實作）。
**不要**在前端 Node 腳本裡重刻簽章，也不要把金鑰塞進前端環境。
`einvoice-acceptance.mjs` 負責走本系統的 HTTP API，平台查證由該 Python 腳本負責，兩者輸出併成證據鏈。

### 11.3.2 第 4、5 項的前置（不做會第一次就卡死）

作廢與折讓**都不是打一支 API 就完成**：

- `decide()` 對折讓與作廢一律 `requires_customer_consent=True` → `create_return` 必須帶
  **已簽署**的 `consent_signature_task_id`，且品項／數量／金額都要對得上
- 同月整筆退且原發票有紙本證明聯（B2C 一般開立就會有）→ `requires_paper_recall=True`，
  未帶 `invoice_recalled` 直接 `ReturnConflict`
- 取得已簽任務需要**已配對的顧客螢幕**（KIOSK）與合法簽名 PNG——而配對是 P2 的
  `04-kiosk-pair` 做的。**PE 排在 P2 之前，得自己先做一次配對。**

### 11.3.3 第 8 項要拆成兩半，否則驗不到那道守衛

`register_manual_invoice` 只有在 `_may_have_reached_platform()`（`posted_at` 非空或
`attempts > 0`）時才向平台查詢。用「沒開立過的單」去登記，會**跳過整段查詢**——
與 §8 的 P2 腳本走同一條窄路，最有價值的守衛根本沒被觸發。

- **8a 從未送出 → 放行**：合成一筆 PENDING 發票直接登記，應成功。
  （註：此情境下「以 `invoice_query` 確認平台沒有那張」是**恆真**，證明力接近零。）
- **8b 可能已送出 → 拒絕**：以 SQL 把一張**已開立**的發票回退成 `PENDING` 並**保留
  `posted_at`**（比照 `09d` 的 `markIssued`／`sql()` 手法），再登記，
  必須被「平台上已經有這筆交易的發票…」擋下。**這一項才是真正的驗證。**

### 11.3.4 第 7 項（retry／result）的前置與語意

- `retry` **只吃 `FAILED`**。而 §8 已排除「統編故意不對」那個手段，所以要製造 FAILED，
  可送一張 **OrderId 已存在**的 F0401（平台明確拒絕 → 佇列轉 FAILED）。
- `record_result` 是 **Turnkey 時代的落庫出口**：狀態驅動只對「已拋檔且仍 PENDING」的列
  生效。Amego 路徑的 `send_via_amego` 是同步收斂成 `UPLOADED`／`FAILED`，
  正常送完的列已是終態。PE 只驗「終態重複回執冪等」與「未認領 → `EInvoiceResultNotApplicable`」，
  **不要期待它改狀態**。

### 11.3.5 佇列端點沒有任何 UI

`send`／`retry`／`result` 三支**只能由店長手動打 API**（全前端無任何 `einvoice/queue` 呼叫）。
§9 要在第 8 章寫作廢與折讓流程時，**必須誠實寫明「送出這一步目前沒有畫面」**，
否則手冊會描述一個不存在的按鈕。此缺口併入第 22 章覆蓋附錄。

### 11.4 前置與風險

- **序號推高是前提**（§2.3）：折讓單號 `L1-1`、`L1-2` 已被佔用，不推高會直接撞號
- 本階段會在 Amego 測試後台留下**真的發票、作廢與折讓紀錄**；測試環境無妨，
  但號碼會真的被消耗，不可無限量重跑
- 執行前先掃號段確認未被佔用（公開共用測試帳號）
- **OrderId 是確定性導出的**（`S{store}-{sale}`）：同一筆銷售一旦開立就**永遠不能再開第二張**。
  PE 若要重跑，必須改用新的 sale，不能重用舊的
- 折讓單號 `L{store}-{allowance}` 同理；且母發票一旦進入作廢流程，其折讓即不可重送
- **PE 執行完要把本輪佔用的 `S`／`L` 號段寫進證據鏈**，供 P2 與日後重跑避開

### 11.5 PE 驗收

- 矩陣九項全綠，輸出平台回應證據
- 在 Amego 後台以肉眼核對至少：一張開立、一張作廢、一張折讓
- 任何一項失敗即停下回報，**不得**帶著未驗證的行為進入 P2 撰寫手冊
