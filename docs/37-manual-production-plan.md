## 2. 四個必須先解決的衝突

裁示彼此組合後產生的矛盾，先在此定案，避免執行到一半才發現。

### 2.1 大量資料 × 真發票

15,000 筆銷售若都開發票，等於送 15,000 張真發票到 Amego 測試環境——不可行也不該做。

**定案**：
- **P0 大量資料在 `einvoice_enabled = false` 下產生**，發票狀態一律 `NOT_ISSUED`
- 只有**手冊腳本要示範的少數幾筆**，在開關打開後真的開立／作廢／折讓
- 這符合 `CLAUDE.md §6`：不論開關，每一筆銷售都完整寫入 `sales`；開關只決定是否產生電子發票

### 2.2 今日交易 × 「尚未開帳」畫面

原始指令 §3.3 要求今日有交易（儀表板不為空）；但今日有現金交易就必須開帳，而手冊腳本 `02-cash-open` 要示範**開帳**畫面（需「尚未開帳」狀態）。

**定案**：seed 今日交易後**把當日班別結掉**。今日資料留著、抽屜是關的，兩邊都成立。
（`docs/34` 已記載 `seed_dev_consignment` 有同樣問題，處置方式一致。）

### 2.3 平台識別碼碰撞（**必踩，已實測確認**）

送到 Amego 的識別碼由本地流水號推導：發票 `S{store}-{sale_id}`、折讓單 `L{store}-{allowance_id}`。
重建資料庫後編號從 1 重來，會撞上前幾輪重跑留在平台上的舊資料。實測結果：

| 識別碼 | 平台狀態 |
|---|---|
| `S1-1` | 已存在（ZA10018786，2026-07-23，$400） |
| `S1-14` | 已存在（ZA10028313，2026-08-03，$270） |
| `S1-20`、`S1-50` | 已存在 |
| `L1-1`、`L1-2` | 折讓單已存在 |

撞號的症狀是「對帳先行」查到舊發票 → 金額或時間對不上 → 判定結果不明 → **開立卡住**，
而錯誤訊息**不會說是撞號**，極易誤判成平台故障。

**定案**：migration 之後、seed 之前執行

```sql
ALTER SEQUENCE sales_id_seq RESTART WITH 300000;
ALTER SEQUENCE invoice_allowances_id_seq RESTART WITH 300000;
```

執行當天**先掃一次號段**確認未被佔用（Amego 測試帳號是公開共用的，別人也會用）。

### 2.4 三種角色 × seed 帳號

三種角色完整寫，需要三個帳號才截得出畫面：

```bash
ALLOW_DEV_SEED=true SEED_USER_PASSWORD=dev-test-123456 \
  uv run python -m app.scripts.seed_dev_user                       # dev-manager / MANAGER
ALLOW_DEV_SEED=true SEED_USER_USERNAME=dev-clerk SEED_USER_ROLE=CLERK \

  SEED_USER_PASSWORD=dev-test-123456 uv run python -m app.scripts.seed_dev_user
```

## 7. P0：模擬營運資料（從頭寫）

### 7.1 取代既有腳本

既有 `backend/app/scripts/seed_dev_demo.py`（276 行，約 120 天大量現金銷售）與本階段重疊。
新腳本 **`backend/app/scripts/seed_demo.py` 取代它**，避免兩份近似腳本並存而分歧。

**沿用它已驗證的手法**：黃金路徑走 `SalesService.create_sale`（確保金額／毛利／庫存口徑正確），
再回填 `created_at` 鋪出時間序（報表一律以 `Sale.created_at` 篩選）。

### 7.2 產生方式（混合策略）

- **黃金路徑**必須經 domain service／應用層，確保狀態機、庫存流轉、現金抽屜、寄售結算等不變條件被真正觸發
- **量體資料**可 bulk insert 加速，但完成後必須跑**不變條件驗證**（§7.5）
- 驗證失敗即視為 seed 失敗，**不得帶著髒資料進入截圖階段**

### 7.3 時間軸與營運節奏

- 涵蓋**最近 12 個月至今日**，含**今日的部分交易**（今日班別最後要結掉，見 §2.2）
- 營業日約 305 天；農曆春節連休 4–5 天；另 2–3 個颱風休業日
- **季節性（台灣露營）**：裝備類 10 月–翌年 2 月旺季，6–8 月淡季（約旺季 40%）；飲品夏季反向上升
- **收購來源季節性**：3–5 月（露季結束出清）與 1 月（年前整理）為送件高峰
- **週間**：週六日約平日 2.5–3 倍
- **時段**：飲品上午小高峰；裝備 14:00–18:00，假日 13:00–17:00 尖峰

### 7.5 不變條件驗證（失敗即中止）

至少檢查：

1. 庫存狀態轉移合法（序號品一旦 `SOLD` 不可再售或重複入庫）
2. 現金階段：開帳零用金 ＋ 銷售現金收入 − 收購付出 − 寄售付款 ± 手動調整 ＝ 結帳應有現金
3. 寄售撥付 ≤ 售出金額；抽成 ＝ `round_ntd(售價 × commission_pct / 100)`
4. 購物金餘額 ＝ 異動流水加總
5. 每筆銷售明細金額加總 ＝ 交易總額
6. 散裝批 `remaining_qty` 不得 < 0；歸零轉 `SOLD_OUT`

輸出 `seed_verification.txt`。

### 7.6 商品與價格

- 二手裝備長尾：眾數 NT$300–1,500，長尾至 NT$15,000–30,000
- 飲品 NT$60–180；新品 NT$150–3,000
- 分類涵蓋：帳篷、天幕、桌椅、睡袋睡墊、炊具爐具、燈具、收納推車、保冷保溫、服飾、配件零件、兒童用品
- **收購價須符合 `CategoryPricingRule` 矩陣與現行定價規則**；不符者不得寫入
- 未達 NT$300 轉售價值者一律走散裝批次，不得產生個別鑑價紀錄

### 7.7 各流程必須涵蓋的狀態（每項至少數十筆）

- 庫存狀態機全部節點（在庫、已售、退回、報廢、滯銷）
- 寄售生命週期：合約成立 → 售出 → 結算撥付 → 未售退回 → 逾期未取
- 簽名任務：`SIGNED`、`CONSUMED`、`VOIDED`、`EXPIRED`、`FAILED` 各須存在
  （注意 `SIGNED` 非終態，必須有被單據 `CONSUMED` 的樣本）
- 現金抽屜：正常結平、短溢、零用金支出、買斷現金支出
- 會員分佈：約 60% 單次、30% 偶發（2–5 次）、10% 常客（6–40 次）；前 10% 貢獻約 40% 裝備營收

### 7.8 假資料安全（強制）

- 姓名用固定合成名單，不得取自任何真實來源
- 電話統一 `0900-000-000`–`0900-000-999`（未配發號段）
- 電子郵件一律 `@example.com`
- **身分證字號與統一編號必須刻意產生檢核碼錯誤的值**，確保永不與真實對象碰撞
- 地址用虛構門牌
- 每筆帶 `is_seed` 旗標，供一鍵清除

### 7.9 可重現與安全

- `--seed <int>` 固定亂數種子，相同種子必須產生完全相同的資料集
